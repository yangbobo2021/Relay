## 基线如何确定

1. 以 [adaptation-baseline.json](adaptation-baseline.json) 中本次修改前各插件提交、对应已发布包及其有效规格/发布记录为旧插件基线，记录包 SHA-256。不要凭当前测试名称推断旧功能已经可用。
2. 为旧组合和新组合各准备独立环境。旧组合使用其已验证的官方 DSH；新组合使用目标提交与当前候选 tarball。固定相同 SDK/CLI、模型配置和合成数据，避免把其他升级混入比较。
3. 从 README、SPEC、验收文档、公开 UI/工具/Remote 能力及已解决问题的回归用例，生成逐项功能目录。每项记录旧版预期、操作、正确结果和用例 ID；完成目录交叉核查后才计算覆盖率。
4. 2026-08-29 的 Codex/Claude 原生产品迁移报告用于发现候选用例，不能直接作为当前插件缺陷表或新版通过证据。它们包含早于后续修复的结论，且“原生产品全部能力”和“旧插件已支持能力”是不同范围。
5. 用合成历史构建“原地升级”副本：相同 Session、Thread/SDK Session 绑定、消息、附件、Wait、Monitor 和 Profile；不得直接改用户生产数据。并行环境不要同时写同一真实后端 Thread。

## 每个关键功能都必须检查的结果

- **正常操作**：用户输入经过真实 DSH→插件→后端/工具→持久化→UI；检查实际文件内容、终端输出、后端 Session 绑定、事件投递目标等结果，而不只检查按钮出现或接口返回 200。
- **拒绝、取消、错误**：审批前没有副作用；拒绝/取消后不继续执行；超时可恢复；错误不会丢失绑定或偷偷建立替代会话。停止进程以实际进程状态/受控文件副作用为准，不仅检查页面显示“已停止”。
- **刷新、重启、升级**：旧历史和附件可读；继续同一会话保留上下文；增量不重复、顺序正确；未完成投递/定时任务按既有语义恢复。
- **组合与隔离**：单插件/必需依赖组合及全部插件同时安装；快速切换 Session、Workspace、模型后端；安装/停用/卸载对其他插件和官方原生聊天的影响。
- **展示等价**：本轮 Codex 在官方 compact 模式下撤销自定义接管，交给原生消息显示。必须检查答案始终可见、过程可展开、工具/图片/产出链接不丢失，以及展开模式、刷新和历史回放；这是明确的呈现变化，不能写成“界面完全未变”。

对 LLM 输出不做易波动的全文相等断言：使用固定目标文件、唯一合成标记、工具轨迹和持久化结果判断；真实模型验收与确定性模拟测试同时保留。

## 发布判定

每条记录至少包含：用例 ID、所属旧功能、旧/新 DSH 提交、插件 tarball hash、SDK/CLI 版本、OS、输入数据版本、操作步骤、旧版预期、新版结果、截图/日志/持久化或副作用证据、状态及复核结论。
状态仅使用 `passed / failed / blocked / not_run`。必测项的 skipped、blocked、not_run 都不能算通过。

发布门槛：

1. 旧插件功能目录逐项关联可执行用例，全部必测项在候选包通过；安全和数据保留场景无失败；代码修复后重跑受影响用例及相邻功能。
2. 旧版成功而新版失败的项目视为回归并阻止发布；旧版已知不支持的能力单独列出，不混算为本次升级引入的回归。
3. 冷启动、旧数据原地升级、失败恢复、全部插件组合，以及承诺支持的 OS 均有本次版本证据。
4. 严格依赖安装检查通过；保留旧包/旧环境和升级前数据副本。回退到隔离的备份环境验证，不能假设新版写入的数据可直接被旧版读取。
5. 通过前仅称“代码适配/部分回归通过”，不称“原有所有功能正常”。通过后也只对记录的版本、平台与场景作结论，不承诺绝对零缺陷。

后续按集中问题清单处理 Claude 识图/fork 和 Codex 提问可用模式，区分已有能力限制与升级回归。
继续补旧附件、Claude 交互式终端导入、扩展能力、管理器完整会话生命周期、真实模型路由、
忙碌/并发及长期恢复、跨平台 CI；候选公开发布后才能复测相应公开来源组合。
第四批部分通过不解除上述发布门槛。
