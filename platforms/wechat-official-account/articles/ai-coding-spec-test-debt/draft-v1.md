# AI 编程越用越不行？真正失控的可能不是模型

刚开始用 AI 写代码时，体验往往很好。

需求很小：加一个按钮、接一个接口、修一个报错。AI 很快改完，我手动点几下，功能正常，就觉得这套方法又快又省心。

项目做了几个月，情况却容易反过来：修好 A，B 坏了；把 B 修回来，之前处理过的 C 又复发。一个问题改很多轮也收不了尾，看起来就像 AI 突然不会写代码了。

我在几个开源插件上持续开发后，越来越觉得，问题不只在模型。更常见的原因是两件事：

1. 产品要求留在聊天里，没有进入项目；
2. 测试覆盖了函数，却没有覆盖用户真正会走的完整场景。

## AI 看到代码，却看不到当初为什么这样做

一次功能为什么这样设计，哪些旧行为绝对不能变，插件之间能不能直接引用代码，发布包必须支持哪些系统，这些要求很容易只存在于某一轮聊天里。

下一次开发时，AI 看到的主要是当前代码。它不知道三个月前为什么放弃了另一个方案，也不知道一段看起来多余的逻辑，其实是在保护真实用户场景。

它只能根据局部代码猜。

这种猜测单独看经常合理，但未必符合产品原意。修改次数越多，偶然形成的行为越容易被后续 AI 当成正式设计继续扩展。

所以 SPEC 不能只是开发前写一次的计划。它要和代码一起留在版本库里，功能边界变化时同步更新，并且回答三个问题：

- 什么可以变；
- 什么不能变；
- 做到什么程度才算交付。

## 测试通过，不等于用户可以正常使用

我做 Codex 对话插件时遇到过一个很典型的问题。

早期实现会直接启动系统里的 `codex` 命令。开发机已经全局安装过 Codex，所以插件能构建，已有测试也能通过。

但普通用户安装插件后，在 DSH 里创建 Codex 对话，只看到：

`spawn codex ENOENT`

代码并不是完全没写，测试也不是假的。真正的问题是：测试环境替我们满足了一个从未写进 SPEC 的前提——用户机器上必须已经有 `codex`。

后来验收要求被改成：插件自己带上固定版本的官方 Codex App Server 运行时；在没有全局 Codex PATH 的环境里验证；macOS、Windows、Linux 分别跑 CI；最后还要在全新目录安装 npm 正式包，启动未经修改的官方 DSH，创建一次真实对话。

这才是在测试用户得到的产品，而不只是测试开发机上的代码。

## 一条成功路径，远远不够

“导入已有 Codex 对话”也经历过类似过程。

最初看起来，只要能把一条 Thread 写进 DSH 就完成了。但真正使用时，还会遇到：

- Workspace 是否只导入自己的对话；
- 标题和最近活动顺序是否保留；
- 重复导入会不会产生副本；
- 中断或失败但已经有回复的 Turn 是否显示；
- DSH 重启后绑定和历史是否还在；
- 同一个 Codex Thread 正被其他客户端使用时怎么办。

这些问题不会因为多写几个函数单测就自然消失。我们最后把导入拆成 14 个风险场景，再增加真实 App Server、官方 DSH 和浏览器验收。

即使这样，浏览器验收仍然发现过自动测试没有拦住的历史加载错误。

![真实浏览器验收暴露了历史加载错误](assets/01-history-load-error.png)

这张图不是在证明测试没用。它说明的是：最终用户路径本身也必须进入测试体系。

## 错误为什么会越藏越深

整个过程通常是这样的：

1. 新要求只写在聊天里；
2. AI 根据局部代码猜产品意图；
3. 自动测试没有覆盖被影响的真实场景；
4. 人工测试靠记忆，漏掉不常用功能；
5. 非预期行为进入下一次开发基线；
6. 后续 AI 又把它当成已有设计继续修改。

积累到一定程度后，提示词写得再详细也只能修补局部。真正缺失的不是某一轮上下文，而是整个项目没有一套持续有效的约束。

## 我现在固定做的七件事

这几个插件后来的开发流程逐渐固定下来：

1. 开发前先列出可以实际交付验收的用户场景；
2. 先更新 SPEC，再修改代码；
3. 每条重要 SPEC 对应自动测试，或者明确的人工验收步骤；
4. 人工验收记录环境、步骤和截图，不再只写“手动测试通过”；
5. 每发现一个缺陷，增加防止它再次发生的回归测试；
6. 每完成一部分，重新检查 SPEC、代码和测试是否一致；
7. 发布前从 npm 正式包和全新环境重新走一次用户路径。

有些界面、跨进程和真实账号场景暂时不适合完全自动化。那就先把它们写成稳定的验收清单并保存证据。等某个场景发生过回归，再尽量把它转成自动测试。

![修复后，冷启动仍能恢复历史并继续原 Codex Thread](assets/02-cold-restart.png)

我现在把 AI 看成一个执行很快、但不会替项目长期保存产品意图的开发者。

SPEC 用来保存意图，场景测试用来阻止旧功能被悄悄改坏。缺少其中任何一个，代码越多，AI 修改的风险就越高。

Relay 和几个 DSH 插件正在公开验证这套方法。仓库里能直接看到 SPEC、插件边界测试、跨平台 CI 和发布验收。感兴趣可以检查这些约束是否真的对应，也欢迎补充我们还没覆盖到的场景：
