# 从选择 Agent 到协调 Agent：Relay 的下一步

[English](from-agent-choice-to-coordination.md) | 中文 | [系列目录](dsh-agent-workbench-series.zh.md)

现在打开一个项目，我可以在 DSH 新建原生、Codex 或 Claude Code 会话。需要实现时
选 Codex，需要第二意见时选 Claude，普通任务留在 DSH。这个工作流已经减少了工具
切换，也把会话重新放回项目下面。

但它仍然依赖一个最勤快的协调者：人。

人决定任务交给谁，人整理上一段会话的结论，人盯着实现何时结束，再把结果拿去审查。
把三个 Agent 放进一个界面，只是统一入口；如果没有任务状态、交接协议和事件驱动，
还不能叫多 Agent 协作。

![当前可用的 DSH 插件工作台实机演示](../media/dsh-plugin-suite-demo.gif)

## 当前已经有的基础

今天可以依赖的能力很具体：

- DSH 按 Workspace 组织用户可见的 Session；
- 每个 Session 明确绑定原生 DSH、Codex Thread 或 Claude Session；
- Files 和 Terminal 读取当前 Session 的项目工作目录；
- Codex、Claude、Workbench 等插件彼此通过公开能力边界组合；
- Relay 仓库已经有 Wait、Monitor、Event、路由和 Delivery 的运行时构件与测试。

最后一项需要谨慎理解。Relay 的事件核心仍在建设，它还不是普通用户安装后就能完成
跨 Agent 编排的成品。现在发布的五个 DSH 插件也不依赖 Relay Events。

## 真正的交接不能只是复制聊天记录

假设 Codex 完成了一次实现，Claude 接下来要审查。最简单的做法是把全部 Codex 对话
塞进 Claude Prompt，但这会带来三个问题：上下文昂贵、噪声很多、责任不清楚。

更可靠的交接应该是一份有结构的任务结果，例如：

- 目标与验收条件；
- 项目和工作目录；
- 已修改文件与关键决策；
- 已运行的测试和失败项；
- 需要下一个 Agent 回答的问题；
- 产物、权限和剩余预算。

完整会话仍可用于追溯，但下一个 Agent 首先拿到的是工作事实，不是一大段未经整理的
聊天历史。这里的上下文压缩不是为了“让模型忘得更聪明”，而是为了形成可靠交接。

## 一个值得实现的闭环

我希望下一阶段先完成一个小而完整的流程：

1. 用户在项目的 DSH Session 中定义任务和验收条件；
2. 根据用户选择或明确策略，把实现任务交给 Codex；
3. Codex 完成后产生结构化结果和 `implementation.completed` Event；
4. Relay 把事件投递给该项目的 Claude 审查 Session；
5. Claude 返回 findings；有阻塞问题就形成修复任务，没有问题则等待用户确认；
6. 所有状态仍回到原项目，用户可以看到每次交接的原因和内容。

这个流程没有追求“十个 Agent 自动开会”。它只验证三件关键事情：任务能否交给正确
Session，结果能否用有限上下文继续，失败能否被用户看见并恢复。

## 成本和质量应该成为策略，而不是口号

多 Agent 协调不应该默认把每一步都发给最贵的模型。策略可以从简单规则开始：

- 日常问题留在 DSH 原生后端；
- 需要仓库执行的任务进入 Codex；
- 高风险改动或用户明确要求时再进入 Claude 审查；
- 超过预算、权限不足或结果不确定时停下来询问用户。

这些规则必须可见、可修改、可覆盖。系统可以建议后端，但用户需要知道为什么选择它，
也需要随时改用另一个 Agent。

## 尚未实现的部分

当前版本尚未实现自动后端路由、跨 Agent 的结构化上下文交接、持久任务图、失败重试
策略，以及完整的协调状态界面。Relay 的 Wait、Monitor 和 Event 构件也还需要经过
真实用户流程打磨，才能作为稳定发行版交付。

因此这篇不是功能发布公告，而是一份实施边界：先把一个 Codex 实现、Claude 审查、
用户确认的闭环做实，再扩展更多 Agent 和外部事件。

项目代码和当前进展在 [Relay](https://github.com/yangbobo2021/Relay)。已经可以使用
的五个 DSH 插件仍然独立发布；关注 Relay，看到的是它们如何从“可选择的后端”走向
“可协调的项目工作”。
