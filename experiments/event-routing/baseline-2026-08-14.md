# Routing Baseline: 2026-08-14

## Environment

- Fixture suite: `email-routing` version 1, 12 cases, 11 critical.
- Fixture SHA-256: `cae248a11fa229febd602fe1c5d8252e1932d2393bef10a56b0acbf2e44b13ab`.
- Codex CLI: `0.147.0-alpha.6.5` using its configured default model.
- Semantic calls: ephemeral, read-only, user configuration ignored.
- Concurrency: 2 cases.

The fixture expectation for an event arriving during a run was clarified after the
model run: a claimed wait can provide routing context but is not claimed again. The
same stored decisions were replayed against that corrected expectation.

## Result

| Metadata | 83.33% | 100% | 88.89% | 75% | 0 | 0 | Fail |

| Two pass | 100% | 100% | 100% | 100% | 22 | 333,489 | Pass |

Metadata routing avoided wrong-session wakeups by escalating conservatively, but it
failed to identify one expected session and treated the newsletter as new work. Both
semantic variants selected every expected disposition, session, and wait without an
exclusive misroute.

The two-pass variant produced no quality improvement on this suite. It doubled model
calls and tokens. Average measured CLI latency per call was about 15 seconds for both
semantic variants.

## Recommendation

Use the single-pass semantic router for the first runtime slice. Keep metadata for
deduplication and broad candidate recall, not as the final decision-maker. Escalate to
a second adjudication pass only after invalid structured output, an unresolved
exclusive conflict, or an actionable `escalate` with plausible existing candidates.

Do not interpret the CLI token count as a production cost estimate. The agent CLI
adds substantial fixed context; a direct model API adapter should be evaluated before
making cost or latency decisions.

## Runtime Integration Check

The production single-pass router and SQLite runtime were connected through the
local Worker CLI and run against `missing_thread_id_same_sender_two_topics`. The
event had no thread metadata and shared a sender with two unrelated sessions. The
router selected only `session-fabrikam-renewal`, matched its approval Wait, and did
not inject into the import conversation. The runtime injected the Event into the
existing inbox, resolved its Delivery, and consumed the matched Wait without creating
a Relay Run.

The check used one configured-default Codex CLI call: 14,662 input tokens, 125 output
tokens, and 16,306 ms. The durable result is local and ignored at
`.tmp/relay-worker-semantic.sqlite`.

## Limits

The suite is small, contains invented messages, and was run once. The configured
default model ID was not exposed in the report. The next evaluation should specify a
model explicitly, repeat each semantic case, and add paraphrase and adversarial-email
variants before setting a production threshold.
